# Divergences from the Lean Kernel

This is a list of places where lean4lean deliberately has different behavior from the kernel. Unless specified here, any divergence between lean4lean and [lean4](https://github.com/leanprover/lean4/tree/master/src/kernel) is a bug.

* [`Lean4Lean.TypeChecker.Inner.reduceNative`](Lean4Lean/TypeChecker.lean): Lean4lean does not support reduction of `reduceBool`. This would involve implementing verified compilation, which while possible would be an additional chunk of work comparable to this entire repo.
* [`Lean4Lean.Environment.checkPrimitiveDef`](Lean4Lean/Primitive.lean), `checkPrimitiveInductive`: Lean does not check that primitives are declared with the correct types and definitional behavior, except in the case of `Eq` which is used in the declaration of `Quot`. This is required for soundness, but Lean is able to get away with it because Lean ships its prelude and using an alternative prelude is not supported. Four aspects of the check are stricter than "declared at a type definitionally equal to the expected one". First, for `Char.ofNat` and `String.ofList`, whose meaning the abstract model pins to a literal type (`∀ _ : Nat, Char` and `∀ _ : List.{0} Char, String`), the declared type is compared with `Expr.eqv` — structural equality up to binder names and binder info — rather than with `isDefEq`. A type such as `(fun _ : Nat => Nat → Char) Nat.zero` is definitionally the right one but is read off structurally as a different constant, so it is rejected. (This is available only for these two; the declared types of the `Nat` primitives carry `@&` borrow annotations, so they have no fixed structural shape to compare against.) Second, the equations for the `Nat` operations are checked under free variables introduced by `withLocalDecl`, so both sides of each comparison are well-typed terms; comparing `∀ _ : Nat, e₁` with `∀ _ : Nat, e₂` to get under the binder would decide the same equations, but on terms that are not types and therefore denote nothing in the model. Third, each branch requires up front that every constant whose *meaning* its equations rely on is already declared — `Nat` and `Bool` wherever the equations mention numerals or booleans, `Nat.ble` for `Nat.div`/`Nat.mod`, `Nat.add`/`Nat.div`/`Nat.mod`/`Nat.beq` for `Nat.bitwise`, `Nat.bitwise` plus `Nat`/`Bool` for `Nat.land`/`Nat.lor`/`Nat.xor`, `String`/`Char`/`List.nil`/`List.cons` for `String.ofList`, and `Nat`/`Bool`/`Nat.beq` inside the well-founded unfolding used by `Nat.gcd`/`Nat.bitwise`. Every one of these was already forced by a subsequent type-checking step in the same branch, so no declaration that used to be accepted is now rejected; stating them as explicit `env.contains` guards makes each branch's semantic dependencies visible, and lets the corresponding `VEnv.HasPrimitives` field be applied directly rather than recovered by inversion on a successful `checkType`. Fourth, the recognizer runs before `checkConstantVal`, so nothing it looks at has been type-checked; it therefore type-checks its own inputs (`checkPrimValue`, `checkIsType`, `checkedIsDefEq`, `checkedTypeIs`, and `withCheckedLocalDecl` for the domain of every free variable it introduces) instead of handing untyped terms to `isDefEq`, and compares against the *inferred* type of `v.value` rather than the declared `v.type`. This covers two distinct sources of untyped input: `v.type` and `v.value` themselves, and the other primitives the equations mention -- `Nat.pred` in the `Nat.sub` branch, `Nat.add` in `Nat.mul`, `Nat.bitwise`'s boolean combinator in `Nat.land`/`lor`/`xor`, and so on -- whose types `VEnv.HasPrimitives` does not pin, so that a right-hand side such as `Nat.add (mul y x) y` need not be well-typed either. Comparing untyped terms was not merely uninformative: `isDefEq` records its verdict in the `EquivManager`, whose well-formedness invariant requires both sides to be translatable, so a declaration such as `Nat.pred : (fun _ : NoSuchType => Nat → Nat) NoSuchValue := fun n => n` left an untranslatable term in that table (`bugs-found.md`). The declaration is rejected either way — `checkConstantVal` catches it a moment later, as does the C++ kernel — so the set of declarations `addDecl` accepts is unchanged, and the Kernel Arena is unchanged at 185/6/0. What does change is *which* check rejects a malformed primitive first, and hence the error message: a `Nat.add` whose declared type is not `Nat → Nat → Nat` now fails on the value's type, or on the mvar/fvar guard, rather than on the declared type. Cost is within noise (65.2 ms after, against 63.4 ms before, for the recognizer plus the body check over all 18 primitives, best of 5 x 40 iterations), and is ~0.08% of the 83 s the Kernel Arena's `init` test spends on 53090 declarations; the body check `addDefinition` runs afterwards shares the recognizer's `inferTypeC` entries.This now covers all eighteen branches: the `Nat.mod`/`Nat.div`/`Nat.gcd`/`Nat.bitwise` branches and the helpers they share (`Reflection.check`/`checkITE`/`checkNatDITE`, `Condition.check`, `unfoldNatWellFounded`, `lambdaTelescope`/`forallTelescope`) were the last holdouts, and the unchecked comparisons there included the recognizer's own literal right-hand sides (`Nat → Nat → Prop`, `Bool → Nat → Nat → Nat`, `fun a _ : Nat => a`, ...) and the domains of binders such as `1 ≤ y` and `Nat.succ x ≤ Nat.succ fuel`; the dead `unfoldWellFounded`, which had no call site anywhere in the tree, was deleted rather than fixed. Every one of those additions leaves the Kernel Arena at 185/6/0. Fifth, the conditional-selection checks the `Nat.mod`/`Nat.div`/`Nat.gcd`/`Nat.bitwise` branches share (`Reflection.checkITE`, `Reflection.checkNatDITE`, and the `.bool` arm of `Condition.check`) are stated on the conditional *application* -- `@ite α p (r.toDec p b H) t e` compared with the branch it must select, under binders `p`, `H`, `t`, `e` -- rather than on a partially applied `fun p b H α => @ite α p (r.toDec p b H)` compared with `fun α a _ => a`. The accepted set is unchanged: `isDefEq` descends under λ and is η-complete, so the equation between the two λ-abstractions holds exactly when all its instances under the binders do, and those instances are what is now checked. Two consequences are worth recording. (i) The result type `α` is no longer universally quantified but passed per call site (`Condition.check` takes an `iteTypes : List Expr` where it took an `ite : Bool`), so `Nat.bitwise`, which needs the rule at both `Nat` and `Bool`, makes two checks. (ii) The old form additionally forced `r.toDec p b H : Decidable p` for a *variable* `b`, via `checkedTypeIs` on `Reflection.ite` / `Reflection.natDITE`; the new form forces it only at `b = Bool.true` and `b = Bool.false`, which is all the abstract statement (`VEnv.ReflectsCondApp`) uses, so the recognizer is very slightly more permissive on `Reflection` records that are ill-typed at a variable boolean and well-typed at both literals. No such record can arise from the two the recognizer ships (`Reflection.defn₁`, `defn₂`), both of which still pass; the check is reachable only from the four fuel/well-founded branches, and the Kernel Arena is unchanged at 185/6/0. The reason for the change is on the verification side: `VEnv.ReflectsCondApp` is stated over the applied form, so its hypothesis is now read off the check by inverting an application spine instead of inverting the translation of a four-fold λ and β-reducing through it. `Reflection.ite` and `Reflection.natDITE` are deleted. Sixth, the `Nat.land` / `Nat.lor` / `Nat.xor` branches now also check that the boolean combinator they destructure out of `Nat.bitwise and` / `or` / `xor` has type `Bool → Bool → Bool` (`checkedTypeIs and q(Bool → Bool → Bool)`), on top of its truth table. This is required for soundness of the abstract statement, not decoration: `VEnv.ReflectsNatBitwise`'s conclusion is an `IsDefEqU` at `Nat.bitwise f (natLit a) (natLit b)`, and `IsDefEqU` entails well-typedness, so the conclusion asserts that `f` inhabits `Nat.bitwise`'s domain; the truth table alone does not imply it (an `f : (x : Bool) → Q x` with `Q Bool.true ≡ Q Bool.false ≡ Bool → Bool` satisfies the truth table at both literals while `Nat.bitwise f` is ill-typed), and without the check the field -- and hence `checkPrimitiveDef.WF.rest` -- was **false**, not merely open. See `docs/handoff-primitive.md` §3. The recognizer is therefore strictly stricter here than before; on the real prelude it passes, since `Nat.land = Nat.bitwise and` with `and = Bool.and : Bool → Bool → Bool`, and the Kernel Arena is unchanged at 185/6/0. Seventh, three further checks were added to the shared conditional machinery, all for the same reason -- the verification cannot recover a term's type from the fact that an application containing it type-checks, because `TrExprS.app` and `VExpr.WF.app_inv` hand back the domain the application *invented*, existentially quantified, not the one the head *declares*. (a) `Reflection.check` now runs `checkType r.toDec`. This is accept-set neutral: `toDec` is a proper subterm of every term `Reflection.checkITE` and `Condition.check` hand to `checkType`, so a `toDec` that fails to type-check already made the branch fail; running it here is what gives the verification a translation of `toDec` at the **base** context, since the ones readable off `checkITE` and off `Condition.check`'s decision term live under binders of different depths and identifying those would need `IsDefEqU.weakN_iff`, which is open. (b) `Reflection.checkITE` and the `.bool` arm of `Condition.check` check the conditional head **already applied to the result type** -- `@ite.{1} α` against `∀ (c : Prop), Decidable c → α → α → α`, once per element of `iteTypes` -- and `Reflection.checkNatDITE` checks `@dite Nat` against `∀ (c : Prop), Decidable c → (c → Nat) → (¬c → Nat) → Nat`. (The `ite` check was first written in the unapplied form, `@ite.{1}` against `∀ (α : Type) (c : Prop), Decidable c → α → α → α`; that form is not usable, because `VEnv.condApp_typed` wants the Pi-type of the head *after* the result type is supplied, and getting there from the unapplied type needs `HasType α (.sort 1)` at the base context, which `checkIsType α` does not give -- it gives `α : Sort u` for an existential `u`, and closing the gap would need type uniqueness plus `IsDefEqU.sort_inv` plus a strengthening step across the recognizer's binders. The applied form hands the verification the Pi-type it consumes directly, and matches what `checkNatDITE` already did. Neither form is a superset of the other in the abstract -- the applied one additionally forces `α : Type`, the unapplied one additionally constrains `ite` at result types never used -- but each is implied by the selection equations the same branch goes on to check, so both are accept-set neutral relative to the rest of the branch, and the Kernel Arena is 185/6/0 for both.) These are strictly stricter -- an environment whose `ite` has some other type is now rejected -- and they are what `VEnv.condApp_typed` / `condApp_typed'` need: without the head's declared Pi-telescope the four arguments of a conditional application cannot be typed, and `VEnv.reflects_condApp`'s selection hypothesis cannot be instantiated at them. Both branches already forced `ite` (resp. `dite`) to be present and to type-check, so no new failure mode appears; the real prelude passes. (c) `Condition.check`'s `.reflectNatNat` arm checks `proof` against `∀ n m : Nat, reflect.type (cond.prop n m) (asBool n m)`, on top of the existing `isProp (← checkType proof)`. Also strictly stricter, and also load-bearing rather than decorative: this typing is `VEnv.reflects_condApp`'s `hPR`, the one hypothesis of its `hsel` that no inversion can recover, and pinning it any other way would need `toDec`'s declared telescope, which nothing checks. `Condition.natLE`'s and `Condition.natEq`'s shipped proofs both have exactly this type. Eighth, the `Nat.bitwise` branch runs its two `Condition.check` calls (`Condition.natEq` at result types `Nat` and `Bool`, `Condition.bool` at `Nat`) **above** the `f` / `n` / `m` binders rather than inside them. Both conditions and both `iteTypes` lists are closed, so neither check reads or binds those variables and the accepted set is unchanged -- only which check reports an error first. The reason is again on the verification side: `VEnv.ReflectsCondApp` is stated at the base context `0 []`, and the facts these checks establish arrived in a context whose `toCtx` was `[Nat, Nat, Bool → Bool → Bool]`; moving them down would have needed `IsDefEqU.weakN_iff` (open) or an instantiation at closed inhabitants. All of Seventh and Eighth leave the Kernel Arena at 185/6/0, measured before and after. Ninth, the two halves of each conditional-selection check -- the `Bool.true` equation and the `Bool.false` one -- are now separate top-level calls (`Reflection.checkITEHalf`, `Reflection.checkNatDITEHalf`, `Condition.checkBoolITEHalf`) instead of two blocks inside one `do`. As two blocks they were **not** two blocks: `fun t => do` opens its `do` block at the same column as the `withCheckedLocalDecl` line that follows it, so in all three places the `false` half was elaborated *inside* the `true` half's binders and ran at binder depth 3 (`p`, `H`, `t` for `checkITE`; `p`, `H`, `a` for `checkNatDITE`; `t` for the `.bool` arm) rather than at the base context. Behaviourally this is inert: the stale local declarations are checked, are mentioned by neither side of the `false` comparison, and are unused, so the accepted set is unchanged (only the local context the second half runs in is larger, and the free-variable ids differ). It is not inert for the verification: `VEnv.hsel_of_checkITE` needs both equations in the *same* four-entry context `[α, α, r.type p b, Prop]`, and identifying the `false` half's conclusion across three stale binders would need `IsDefEqU.weakN_iff`, which is open. Factoring each half into its own definition makes the two calls siblings by construction, so the layout cannot silently regress. Kernel Arena 185/6/0 before and after, measured over two full runs. Tenth, three statements of `Condition.check`'s `.reflectNatNat` arm were reordered: `checkType e` moved from above the `asBool` / `proof` checks to immediately before `isDefEq e cond.dec`, and `if dite then reflect.checkNatDITE fail` moved from just after the `iteTypes` loop to the arm's last statement. Every statement in the arm must succeed for the recognizer to accept, and none of the moved statements reads state produced by the ones it moved past, so the accepted set is unchanged; what changes is which check rejects a malformed `Condition` first, and hence the error message. Both moves are for the verification. (i) `checkType e`'s output is a translation of the decision term `fun x y => toDec (prop x y) (asBool x y) (proof x y)`, and that translation can only be *read* -- by `trExprS_decisionTerm_inv'`, which identifies its four abstract subterms with base-context translations -- once `proof`'s own base-context translation exists, and the check that produces it is `checkedTypeIs proof (∀ n m : Nat, …)`. In the old order `checkType e` ran first and its output mentioned a translation of `proof` that nothing later could be identified with. (ii) A trailing `if` in a `do` block needs no join point: with the `dite` test last, the arm's tail is a single continuation the proof traverses once, where in the old order Lean's `do` elaborator duplicated the whole tail into both branches of the test through a `__do_jp` join point. Kernel Arena 185/6/0 before and after. Eleventh, the `Nat.gcd` and `Nat.bitwise` branches -- the two that go through `unfoldNatWellFounded` -- now make three further checks, and the first of them is required for soundness of the abstract statement rather than for convenience. (a) **The measure.** `unfoldNatWellFounded` recovers `WellFounded.Nat.fix α motive h F a₀` from the definition's value and now checks `h (pack fvs) ≡ μ` for a measure `μ` the branch supplies (`m` for `Nat.gcd`, `n` for `Nat.bitwise`), where `pack` is the recovered packing `fun fvs => a₀`. Nothing previously constrained `h` at all, and `WellFounded.Nat.fix h F x` unfolds to `fix.go h F (Nat.eager (h x + 1)) x _`, where `Nat.eager` is a gadget whose documented purpose is to *block* reduction until its argument is ground: so a definition whose measure the kernel cannot evaluate does not reduce at numerals at all, while passing every check the recognizer made. `VEnv.HasPrimitives` demands the opposite (`ReflectsNatNatNat ``Nat.gcd Nat.gcd` is an `IsDefEqU` at numerals), so without this check the field -- and hence `checkPrimitiveDef.WF.rest` -- was **false**, not merely open. The witness is `scripts/primitive-wf-refutation.lean`: a `Nat.gcd` with the real body and `termination_by m + 0 * Classical.choice ⟨0⟩` was accepted, while the Lean kernel refutes `gcd 4 6 = 2` by `rfl` on it; the same trick works on `Nat.bitwise`. Both witnesses are rejected after the change and both real primitives are still accepted, measured before and after. (b) **The fuel recurrence.** Both branches now also check `fix.go h F (Nat.succ fuel) (pack fvs) hb ≡ …`, with the recursive call at `fix.go h F fuel (pack …) _`, under fresh `fuel` and a fuel bound `hb` whose domain is read off `fix.go`'s own type. This is the shape the *proved* `Nat.mod` and `Nat.div` branches use. It is needed because the fixpoint equation the recognizer already checked pins `F a₀` at exactly one `ih` (`fun y _ => fix h F y`), and an `IsDefEqU` at one argument implies nothing at another, so no fuel induction could evaluate `F` at `fun y _ => fix.go h F fuel y _`. (c) Two conversions that `whnfCore`/`unfoldDefinition` merely *found* -- `mkAppN e fvs ≡ fix h F (pack fvs)` and `fix h F a ≡ fix.go h F (Nat.eager (h a + 1)) a _` -- are now re-established by `checkedIsDefEq`. Those are accept-set neutral (both hold definitionally wherever the reduction found them), and the point is that the verification then needs no specification of `whnfCore` or `unfoldDefinition` at all. Consequences for the accepted set: the two branches are strictly stricter, and they now require more of the environment. `Nat.gcd` additionally needs `Nat.pos_of_ne_zero`, `Nat.mod_lt`, `Nat.lt_of_lt_of_le`, `Nat.le_of_lt_succ` (to build the recursive call's fuel bound) and `Condition.natEq`'s `dite` machinery (`Not`, `@dite Nat`, `Nat.decEq`, `Nat.beq`, `Nat.eq_of_beq_eq_true`, `Nat.ne_of_beq_eq_false`); `Nat.bitwise` additionally needs `Nat.div_lt_self`, `Nat.le.refl` and the same `dite` machinery, and its `Condition.natEq` check now runs with `dite := true`. Every one of these already precedes `Nat.gcd`/`Nat.bitwise` in Lean's own prelude -- they are what those two definitions' own termination proofs are built from -- so the Kernel Arena is unchanged at 185 correct / 6 either / 0 incorrect; an environment declaring `Nat.gcd` before them would now be rejected where it used to be accepted. **Twelfth**, `unfoldNatWellFounded` is now *search only*: nothing it returns is trusted, and every fact the verification uses is re-established by a check its **caller** makes. Three checks were added and two were removed. Added: (i) `fix.go`'s **own type**, `∀ (fuel : Nat) (x : α), Nat.succ (h x) ≤ fuel → motive x`, checked at the base context — without it the recursive call's fuel bound has no type at all (`VExpr.WF.app_inv` invents an existential domain), and the fuel induction's step hypothesis is underivable; this is the exact counterpart of the `Nat.mod` branch's `checkedTypeIs q(Nat.modCore.go) q(…)`; (ii) the types of the measure (`α → Nat`) and of the packing function (`Nat → Nat → α`, resp. `(Bool → Bool → Bool) → Nat → Nat → α`), also at the base context, which is what makes their translations closed; (iii) that `go`, `pack`, the measure, the carrier and the motive contain **no free variables** (`checkNoMVarNoFVar`) and **no projections** (`noProj`, a `Lean4Lean.anySubterm` scan — not a fresh recursion, so `Verify/Guard.lean`'s implementation-gap list does not grow). The fvar check is load-bearing rather than hygienic: the induction steps `go` and `pack` to *different* arguments, so both must be the same closed terms at every level of the recursion, and nothing previously forced that — `whnfCore` of `e m n` may perfectly well return a `fix α motive h F a₀` whose `α`, `motive`, `h` or `F` mention `m` or `n`. Removed: the fixpoint equation `rhs ≡ F a₀ ih` (it was checked at exactly one `ih` and no fuel induction can use it — see clause Eleventh (b)) and the structural check that `fix.go`'s unfolding is a `Nat.rec` over the fuel (the caller's fuel recurrence subsumes it semantically). Two placements also changed: `Condition.bool`'s check moved out of the unfolder into the two branches, because it must run where the local context is empty; and the fuel bound's binder domain is now written out as `Nat.succ (h (pack …)) ≤ Nat.succ fuel` rather than read off a `whnf` of `go`'s type, so no specification of `whnf` is needed. `Nat.gcd`'s guard correspondingly gained `Bool` and `Nat.beq`, which the unfolder used to require internally. Net effect on the accepted set: the removed checks widen it, the added ones narrow it; the eighteen primitives of the current prelude are still accepted (the `run_meta` self-test at the foot of `Lean4Lean/Primitive.lean`), both witnesses of `scripts/primitive-wf-refutation.lean` are still rejected, and the Kernel Arena is unchanged at 185 correct / 6 either / 0 incorrect, measured before and after. `Lean4Lean/Primitive.lean` now imports `Lean4Lean.Inductive.Add` for `anySubterm`.
* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), literal case: The original code was not checking that the literal type actually exists. Again, this is okay provided that the prelude is trusted.
* [`Lean4Lean.TypeChecker.Inner.tryStringLitExpansionCore`](Lean4Lean/TypeChecker.lean): there is a counterproductive `whnf` call in this function which is removed in Lean4lean.
* [`Lean4Lean.TypeChecker.Inner.isDefEqApp`](Lean4Lean/TypeChecker.lean): lean4lean compares the two argument counts before the two heads, where `type_checker::is_def_eq_app` compares the heads first. Both answer `false` when the counts differ, so the decision is the same.
* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), application case: lean4lean checks `isDefEq dType aType`, where `infer_app` checks `is_def_eq(a_type, d_type)`. Definitional equality is symmetric, so this cannot change the answer, but this avoids some needless left-right flipping.
* [`Lean.Level.normalize`](https://github.com/leanprover/lean4/blob/v4.33.0-rc2/src/Lean/Level.lean), `isEquiv`, `geq`, `instantiateLevelParams`: Lean4lean uses the level operations from Lean's standard library, which differ from the C++ kernel's; [leanprover/lean4#14356](https://github.com/leanprover/lean4/pull/14356) tracks aligning them. This has two separate consequences. The comparison operations decide slightly different sets of (in)equalities than the kernel's `is_equiv`/`is_geq` (but see the next point). And because `instantiateLevelParams` builds levels with `mkLevelMax'`/`mkLevelIMax'` rather than the kernel's `mk_max`/`mk_imax`, unfolding a universe-polymorphic constant can produce a term that means the same as the kernel's but is not syntactically equal to it, and so does not share its `Expr.hash`.
* [`Lean.Level.normalize'`](Lean4Lean/Level.lean), `isEquiv'`, `geq'`: Lean4lean implements a new algorithm for level normalization. These run the standard library's operation as a fast path and fall back to a complete decision procedure for level algebra, so lean4lean decides level equality and `≥` for *more* pairs than either the standard library or the kernel — it accepts declarations the kernel rejects for reasons of level incompleteness, never the other way around.
* [`Lean4Lean.checkConstantVal`](Lean4Lean/Environment.lean): The original implementation would call `check` which sets the level params and then unsets them afterward, and then `ensure_sort` would run in a context without any level params. In lean4lean the monad is parameterized over level params, so they remain the same across the two calls.
* [`Lean4Lean.toCtorWhenStruct`](Lean4Lean/Inductive/Reduce.lean), `inferProj`: both kernels now recognize `Prop` using normalized universe levels ([leanprover/lean4#14613](https://github.com/leanprover/lean4/pull/14613)). Lean4lean remains more conservative for uncertain levels, using `isNeverZero` where Lean uses `!isAlwaysZero`. Lean's choice would be unsound if its level algorithm did not reject the true equation `imax 1 u ≤ u`: `inductive T.{u} : Sort u where mk : Bool → T` would otherwise permit an analogue of the construction in #14613.
* [`Lean4Lean.EquivManager.isEquiv`](Lean4Lean/EquivManager.lean), [`Lean4Lean.TypeChecker.Inner.isDefEqCore'`](Lean4Lean/TypeChecker.lean), `reduceProj`: when comparing two projections, and when reducing one, lean4lean uses only the projection index, while the C++ kernel also compares the structure name ([leanprover/lean4#14631](https://github.com/leanprover/lean4/pull/14631), [#14632](https://github.com/leanprover/lean4/pull/14632)). The name has already been checked by the time either happens: [`inferProj`](Lean4Lean/TypeChecker.lean) rejects `.proj S i e` unless the type of `e` whnfs to an application of `S` itself. Comparison and reduction only ever see projections that have been through type inference, so re-comparing the name there is redundant.
* [`Lean4Lean.Environment.addInductive`](Lean4Lean/Inductive/Add.lean): [leanprover/lean4#14621](https://github.com/leanprover/lean4/pull/14621) rechecks the declarations produced by nested-inductive elimination — the restored constructor types, the restored recursor types and the recursor rules' right-hand sides. Lean4lean does not. Upstream describes these as redundant sanity checks that "may prevent soundness bugs if the nested-inductive code is still missing any required validations"; they establish no precondition that a later step consumes. Lean4lean aims to prove the elimination correct rather than to recheck its output, and a speculative check would only add proof obligations without contributing an invariant. The check of the nested applications `I Ds` from [#14577](https://github.com/leanprover/lean4/pull/14577) is kept, because those arguments are dropped from the auxiliary declarations and so are not covered by checking the block.
* [`Lean4Lean.checkNoNestedAux`](Lean4Lean/Inductive/Add.lean): [leanprover/lean4#14616](https://github.com/leanprover/lean4/pull/14616) rejects the reserved `_nested` prefix in both the inductive types and the constructor types of a declaration; lean4lean checked only the constructor types **until 2026-09-01, when the member-type call was added, so the two now agree and this bullet's premise is stale** — kept because the *reasoning* below is what justified the omission and is worth preserving. *Was:* lean4lean checks only the constructor types. The bug that check fixes is specific to constructors: nested occurrences are rewritten to the auxiliary types in constructor types only (`replaceAllNested`), and rewritten back the same way (`restoreNested`), so an inductive's own type is carried through both directions verbatim and cannot acquire a type it was not checked at. A `_nested` name written in an inductive type also cannot resolve in the first place: the auxiliary types are declared in the same block, so they are not in the environment while that block's types are checked (unlike constructor types, which are checked once the block's types, auxiliaries included, are present), and they never survive into the final environment. Lean's check additionally reserves the whole `_nested` namespace against unrelated user declarations, which lean4lean does not.
* [`Lean4Lean.ElimNestedInductive.Result.restoreNested`](Lean4Lean/Inductive/Add.lean), `restoreCtorName`: [leanprover/lean4#14632](https://github.com/leanprover/lean4/pull/14632) turned the `lean_assert`s in the nested-inductive restoration into kernel exceptions; lean4lean keeps `unreachable!` and `assert!`. The branches are unreachable: `restoreCtorName` runs only for the recursors of the auxiliary types the elimination generates, whose constructors are exactly the keys of `aux2nested`, and the nested occurrences stored there are applications of a constant by construction. Upstream's stated motivation is that the assertions vanish in a release build and the C++ consumers then read out of bounds; the corresponding accesses here are total, so there is nothing to read out of bounds. Note that if one of these invariants were broken anyway, `unreachable!` would continue with a default value rather than reject; the restored constructor and recursor types are re-checked in the final environment ([#14621](https://github.com/leanprover/lean4/pull/14621)), which lean4lean retains, but a restored rule constructor *name* is not covered by that pass.
* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), `.bvar` case: `type_checker::infer_type_core` writes `lean_unreachable()` in the `BVar` case; lean4lean throws the same `Kernel.Exception` the function's own entry guard throws for loose bound variables. The branch is unreachable in both: `infer_type_core` and `inferType'` both open with `if (has_loose_bvars(e)) throw …`, and a bare `.bvar i` has `looseBVarRange = i+1 > 0`, so it never reaches the `match`. The difference is only in what happens if that reasoning is ever wrong. `lean_unreachable()` is undefined behaviour in a release build; `unreachable!` in Lean is a `panic!`, i.e. `fun _ _ s => .ok (default, s)`, which *continues* with `default` — for `inferType'` that means returning an arbitrary `Expr` as the inferred type of a term, which is unsound. Throwing rejects instead, which is sound unconditionally. This also removes the branch's dependence on the [`looseBVarRange_eq`](Lean4Lean/Verify/Axioms.lean) axiom: `Expr.hasLooseBVars` reads the cached `looseBVarRange` field of the expression's `Data` word rather than recomputing it, and that field was not conservative before the fix of [leanprover/lean4#8554](https://github.com/leanprover/lean4/issues/8554) (`bugs-found.md`), so "the guard above already rejected every `.bvar`" is a claim about upstream data-word arithmetic, not a claim about the `match`. `inferType'.WF` now discharges the case with `.throw` — a rejection satisfies every `Except.WF` obligation vacuously — instead of deriving a contradiction from the guard. The set of accepted declarations is unchanged (Kernel Arena 185/6/0); no reachable input takes this branch. The same argument applies to the remaining `unreachable!`s in `getSortLevel`, `whnfCore'`, `isDefEqCore'` and `quickIsDefEq`, which have not been converted.
* [`Lean.Expr.cheapBetaReduce`](Lean4Lean/Instantiate.lean): where the C++ kernel drops the consumed arguments outright when `!fn.has_loose_bvars()`, lean4lean applies the (then trivial) substitution, returning `mkAppRange (fn.instantiateRevRange 0 i args) i args.size args`. `Expr.hasLooseBVars` reads the cached **20-bit** `looseBVarRange` field of the `Data` word, so it is `< 2^20` unconditionally and is wrong for a term whose `bvar` indices overflow it ([leanprover/lean4#8554](https://github.com/leanprover/lean4/issues/8554), `docs/axiom-audit.md` §3.1). If that bit ever reported "no loose bvars" for a body that has them, the C++ form would silently drop a substitution that is needed, which is unsound; the form here is a beta reduction whichever way the bit falls, so `BetaReduce.cheapBetaReduce` needs no side condition. When the bit is honest — always, at run time, since `lean_expr_mk_data` calls `lean_internal_panic` ("too many bound variables") and *aborts* rather than building such a term — `instantiateRevRange` is the identity and the value computed is unchanged. The C `lean_expr_instantiate_rev_range` returns immediately when the cached range is `0`, so the fast path is preserved too.

* [`Lean4Lean.TypeChecker.Inner.isDefEqLambda`](Lean4Lean/TypeChecker.lean), `isDefEqForall`: the C++ kernel skips the local declaration when `tBody.has_loose_bvars() || sBody.has_loose_bvars()` is false, pushing a placeholder into `subst` instead of a free variable; lean4lean always introduces the free variable. Same reason as `cheapBetaReduce` above: the test reads the untrustworthy cached 20-bit field, and a bit that wrongly said "no loose bvars" would have the two bodies compared with `default` (an undeclared constant) substituted for the binder — an instance check where a check under a binder is required. Whenever the bit is honest the two branches decide the same thing, because neither body looks at the pushed value, so the set of accepted declarations is unchanged (Kernel Arena 185/6/0). The cost is an extra local declaration, and an extra `sDom.instantiateRev subst`, per binder pair: 6% wall-clock on the whole Kernel Arena suite (251.3 s to 267.5 s), with the two large tests `init` (83.5 s to 89.1 s) and `std` (139.4 s to 148.0 s) accounting for essentially all of it and no `perf/*` test moving more than 5%.

* [`Lean4Lean.FuelConfig`](Lean4Lean/FuelConfig.lean): since [leanprover/lean4#13956](https://github.com/leanprover/lean4/pull/13956), the native kernel bounds mutually recursive checking through the `maxRecDepth` option. Lean4lean exposes several independent fuel counters instead, because its Lean definitions also need explicit termination witnesses. * [`Lean4Lean.addDefinition`](Lean4Lean/Environment.lean) (`unsafe` branch), [`addMutual`](Lean4Lean/Environment.lean): an `unsafe`/`partial` definition may be recursive, so its body is checked in an environment that already contains the declaration. The C++ kernel adds `constant_info(d)` there -- the full definition, value included -- so the body can delta-unfold the very constant being defined. Lean4lean adds it as an axiom of the same type instead: the body may still *refer* to the block's constants, but cannot unfold them. So for example `unsafe def foo : Nat := (fun (_ : foo = 1) => 1) rfl` is accepted by the C++ kernel, but rejected by L4L: checking the argument requires `foo =?= 1`, which succeeds by unfolding `foo` to its own body and reducing. Read literally, that rule makes a typing fact about the constant available while establishing it, and implementing this in `IsDefEq` directly degenerates completely, allowing even things like `unsafe def bar : Nat := "hi"` by using the typing judgment to justify itself. The gap is confined to `unsafe`/`partial` code, which carries no logical content.
* [`Lean4Lean.addMutual`](Lean4Lean/Environment.lean): lean4lean requires the declarations of a mutual block to carry the same universe parameters and to have distinct names. Both checks are in kernel PRs that are not yet released ([leanprover/lean4#14608](https://github.com/leanprover/lean4/pull/14608), [#14632](https://github.com/leanprover/lean4/pull/14632)); the released kernel checks only that the safety annotations agree. Lean4lean needs them rather than merely matching them: the block is checked under a single `M.run`, whose level parameters are fixed for the whole run, and the model adds the block's constants one at a time with `VEnv.addConsts`, which fails on a repeated name.
* [`Lean4Lean.VEnv.ParRed`](Lean4Lean/Theory/Typing/ChurchRosser.lean), `CParRed` (`K⁺` rule).

  > **CORRECTION.** This entry was written as a description of the tree and is a description of an
  > *intended design*. **None of the machinery it names exists**: `ParRed` has no `K⁺` rule, and
  > `Params` has neither `pat_small` nor `pat_major_canonical` — `Theory/Inductive/Lemmas.lean:150`
  > says so outright. Read the paragraphs below as the design rationale they are, not as a
  > divergence in force.
  >
  > The rule now exists in a **different and stronger form**: `Theory/Typing/KRule.lean`'s `KStep`
  > is indexed by **`Pat`, not by "small-eliminating inductive"**, which is what lets it cover the
  > *quotient* rule as well. Measured by kernel-checked `rfl` probes: `Eq` reduces under the
  > checker's `toCtorWhenK`; `Acc` does **not** (the reference's `K⁺` covers it, the kernel does
  > not); `Quot` over a `Prop` carrier reduces under **neither** — `KStep` covers all three.
  >
  > **And no divergence is owed on soundness grounds.** `toCtorWhenK` is *admissible* in
  > `IsDefEq` (its guard forces a `Prop` major premise), and `Verify/` never relates `addDecl` to
  > `Pat`/`ParRed`. The real gap is **completeness of `Theory/`'s reduction relation**, not the
  > implementation escaping its specification. See `docs/handoff-krule.md`.

  The intended design, retained for its rationale: the abstract parallel-reduction relation fires an ι-rule on a major premise that is not syntactically a constructor application, whenever the major premise's type is a `Prop` and the eliminator is not small (`¬pat_small`, i.e. `D.isLE = true`). The kernel does not: `toCtorWhenK` runs only when `isKTarget` holds — a single type, an `isAlwaysZero` level, and a single constructor **with no fields** — so `Eq` qualifies but `Acc` does not, and `Acc.rec C f x h` is a weak-head normal form for the checker while `Acc.rec C f x (Acc.intro x g)` reduces. The abstract relation is therefore strictly larger than the checker's reduction on exactly these terms.

  This is deliberate and it is forced. `NormalEq.parRed`'s `appDF`/`extra` case must produce a *common reduct*: from `f a ≡ₚ f₂ b` and an ι-step on `f₂ b`, it has to exhibit `e₁'` with `f a ≫* e₁'` and `e₁' ≡ₚ e₂'`. When `a ≡ₚ b` holds by `NormalEq.proofIrrel` — `a` an arbitrary proof, `b` a constructor application — no axiom about inductive declarations can close it, because every such axiom delivers a *definitional* equality `a ≡ b` while `≫*` is syntactic reduction. Carneiro's `K⁺` (`unique.tex:103`) is stated with a typing side condition precisely so that it can fire on an arbitrary `h`, and his `thm:gg_compat` discharges the case by asserting "it is a small eliminator" — which is exactly `pat_small`, and which is false for `Acc` and `Eq`. So the rule, not a side condition, is what does the work; `Params.pat_major_canonical` supplies only the canonical form and its typing, to justify the new rule's regularity (`ParRed.defeq`) and its orthogonality (the `pat_uniq` family).

  Soundness is unaffected. `kernel_sound` needs "the checker accepts ⟹ the abstract environment is well formed", so enlarging the abstract theory is the direction that helps; the burden moves to the consistency of the enlarged theory, and the model discharges it — every proof is interpreted as the single point, and `K⁺` fires only when the major premise is a `Prop`, so proof irrelevance validates it with no further hypothesis.

  What it costs: [`reduceRecursor.WF`](Lean4Lean/Verify/TypeChecker/WHNF.lean) can no longer be read off the `ParRed` development as an equality between the checker's reduction and the abstract one. It has to be proved as a *containment* — the checker's `whnf` step is one of the abstract relation's steps — with the `K⁺` steps simply having no checker counterpart. If that proof refuses to be an equality, this is why. A second, smaller cost: `CParRed.exists` becomes non-constructive, since deciding whether to fire `K⁺` needs the major premise's `Prop`-ness and the existence of a canonical form; `Classical.choice` is already in `Verify/Guard.lean`'s whitelist and the whole development is in `Prop`.

* [`Lean4Lean.anySubterm`](Lean4Lean/Inductive/Add.lean) (`hasIndOcc`, `isNestedInductiveApp?`, `checkNoNestedAux`): these three "does any subterm match?" tests used `Lean.Expr.find?`, i.e. [`Lean.Expr.findImpl?`](https://github.com/leanprover/lean4/blob/v4.33.0-rc2/src/Lean/Util/FindExpr.lean), an `@[extern "lean_find_expr"] opaque` constant with **no Lean body at all** — not `partial`, not `@[implemented_by]`, so nothing to unfold and nothing to prove about. `hasIndOcc` is what `checkPositivity` rejects on, so strict positivity — one of the two places an inductive declaration can be unsound — rested on a C function with no Lean-side model, and `Verify/Guard.lean`'s check 3 does not see it (it filters to constants defined in `Lean4Lean.*` modules). Since all three consume the result only through `.isSome`, the question is purely existential and the C traversal's order, short-circuiting and pointer cache are invisible to the answer; `anySubterm` asks it with a structural walk built on the repo's own total `Lean.Expr.replaceNoCacheT`, which visits exactly the node set `for_each_fn<true>` does (`~/lean4/src/kernel/for_each_fn.cpp`), and `Lean.Expr.findImpl?` leaves the checker's cone entirely. No new axiom, and `Verify/Guard.lean`'s check-3 count is unchanged at 54/54 — the walk introduces no new recursive constant, which matters because *every* recursive definition, structural or not, gets an `f._unsafe_rec` companion for code generation and check 3 counts those.

  **The divergence is in complexity, not in the answer.** `lean_find_expr` caches visited nodes on pointer identity, so it is linear in the *DAG*; `anySubterm` has no cache and is linear in the *tree*, so a term with shared subterms is walked once per path to it. On real input this is invisible: over the 314073 type and value expressions of a full `Lean` environment the uncached walk costs 1.6x on a predicate that never fires and 1.1x on one that fires early, and the Kernel Arena is unchanged within noise (`init` 84.3 s -> 85.3 s, mean of 3; `std` 148.2 s -> 138.9 s, mean of 2; suite 185/6/0 either way). On *crafted* input it is exponential: an inductive whose constructor argument type is a maximally shared DAG of `n` nodes (`t 0 = 1`, `t (n+1) = Nat.add (t n) (t n)`, constructor `mk : Fin (t n) -> Foo`) is accepted through `Lean4Lean.addDecl` in 9 ms for every `n` up to 1000 with `find?`, and in 51 ms / 664 ms / 2511 ms for `n` = 16 / 20 / 22 with `anySubterm` — a ~40-node declaration would hang the checker. The export format shares subterms by index, so such an input is constructible. Restoring linearity needs a visited-set keyed by an `Expr` equality, and the only ones available are upstream `@[extern] opaque` constants: `Expr.equal` (via `ExprStructEq`, modelled by the frozen `equal_eq` axiom but not currently in the cone) or `Expr.eqv` (in the cone, modelled by `eqv_eq`). Either would make the *answer* depend on an extern, which is what this change exists to undo, so the cache is deliberately omitted.

    inside the band already recorded for that entry (`init` 1.4 min, `std` 2.4 min), and the
    sharing-stress cases in the `perf/` group are unmoved: `perf/shared-subterm` 77 ms,
    `perf/identical-nesting` 42 ms, `perf/repeated-subproblem` 39 ms, `perf/let-ladder` 979 ms.
    No crafted worst-case input was constructed for this path; the argument above (the cached
    `hasLevelParam` bit prunes every monomorphic subterm in `O(1)`) is why the hot path does not
    move, and it is an argument, not a measurement of the worst case.

* [`Lean4Lean.checkEqType`](Lean4Lean/Quot.lean): lean4lean **rejects a quotient initialization whose `Eq` is an `unsafe inductive`**; the C++ kernel's `check_eq_type` (`~/lean4/src/kernel/quot.cpp`) accepts it. Concretely, the input treated differently is any environment in which `Eq` is declared as an inductive with one universe parameter, one constructor, and the exact type and constructor type `check_eq_type` demands, but with `isUnsafe := true` — for example the `prelude` file

  ```lean
  prelude
  universe u
  unsafe inductive Eq : {α : Sort u} → α → α → Prop where
    | refl : ∀ {α : Sort u} (a : α), Eq a a
  init_quot
  ```

  which the C++ kernel accepts (verified: it elaborates with no error, and `#print Eq` reports `unsafe inductive Eq`). lean4lean now answers `failed to initialize quot module, 'Eq' is not a safe declaration`. Nothing else about `checkEqType` changes, and every environment the C++ kernel accepts with a *safe* `Eq` is still accepted. Because `Eq` is safe in every real prelude, no test in the Kernel Arena is affected: 185 correct / 6 either / 0 incorrect before and after.

  **Why the divergence is required.** `addQuot` installs `Quot`, `Quot.mk`, `Quot.lift` and `Quot.ind` with `Environment.add` (C++: `add_core`), bypassing the type checker, and a `quotInfo` constant is unconditionally safe. `Quot.lift`'s type mentions `Eq`. So without this check both kernels mint a *safe* constant whose type names an *unsafe* one — exactly what `TypeChecker.inferConstant` (C++ `type_checker::infer_constant`) rejects in every other syntactic position. On the proof side the consequence is sharper: `TrEnv'.quot` is the only constructor that sets `quotInit`, and its first premise is `VEnv.QuotReady env`, so `TrEnv safety env venv` with `env.quotInit = true` forces `Eq` into the model and hence visible at `safety` — at `.safe`, forces `Eq` to be a safe declaration (`TrEnv.eq_visible_of_quotInit`, `Verify/SafeFragment.lean`). An unsafe `Eq` is additionally in *no* model at *any* level, since `TrEnv'.induct` is gated to safe blocks (positivity is skipped when `isUnsafe`). So without this check `∃ venv, TrEnv .safe env venv` after the `.quotDecl` step is **false**, and `addQuot.WF` is unprovable rather than merely unproved. See `bugs-found.md` entry 15 and `Lean4Lean/Verify/EqSafety.lean`.

  **What is deliberately *not* checked.** Only `Eq`'s own safety tag. `checkEqType` also looks up `Eq`'s single constructor and checks its type; its safety tag is left alone, because `VEnv.QuotReady` and the `quotInfo` types mention `Eq` and not `Eq.refl`, so the constructor's tag is not part of the obligation. (An inductive declared through either kernel gives its constructors the block's tag anyway, so the two can differ only in a hand-built environment.)

* [`Lean4Lean.LocalContext`](Lean4Lean/Std/LocalContext.lean): the kernel's local context is a
  `Std.HashMap FVarId LocalDecl` plus an `Array (Option LocalDecl)`, where the C++ kernel (and
  `Lean.LocalContext`) uses a persistent hash-array-mapped trie and a persistent array. Every
  operation the kernel performs returns the same value; the `auxDeclToFullName` field, which the
  kernel never writes, is dropped. **Complexity differs**: `Array.push`/`Std.HashMap.insert` are
  O(1) amortised when unshared but copy when shared, and the context is shared across
  `withReader` frames, so building an n-binder telescope is O(n²) rather than O(n log n). Local
  contexts are telescope-sized, so this is not observable at any size the arena reaches. The
  `Lean.Kernel.Exception` payloads still carry a `Lean.LocalContext`, rebuilt at the throw site,
  so error messages are unchanged.

* [`Lean.Kernel.Environment.empty`](Lean4Lean/Environment/Basic.lean), `finalizeImport`: the
  constant map is built at `SMap` **stage 1**, so added constants go into the `Std.HashMap` half
  rather than the `PersistentHashMap` half. Lookups agree exactly. **Complexity differs**, and
  upstream's own comment in `Lean4Lean/Replay.lean` named it: the replay state holds the
  environment while a declaration is being added, so the map is shared and each insert copies its
  bucket array — O(n) per declaration, O(n²) for a whole module, against O(log n) per declaration
  for the persistent map. Measured: `--fresh Init.Core` (n ≈ 4000) is unchanged (6.71 s vs
  6.91 s); the Kernel Arena's `init` test is ×1.19 and its larger `std` test ×1.40, so **the ratio
  grows with module size**, and it has **not** been measured at Mathlib scale. Total arena wall
  time +28%, concentrated in those two tests; everything else ≈×1.0. If it ever bites, the fix is
  to remove the *sharing* in `Replay.lean`, not to revert the stage.

  Both changes exist to remove the four `PersistentArray`/`PersistentHashMap` axioms. Their
  subjects are `partial` upstream, and a `partial def` elaborates to an **`opaque` constant**:
  all eight helpers carry 0 equation lemmas and no unfolding theorem, so *nothing whatever* can be
  proved about them — not even `PersistentHashMap.empty.find? k = none`. See
  `docs/handoff-containers.md`.

* [`Lean4Lean.TypeChecker.Inner.reduceBinNatOp`, `reducePow`](Lean4Lean/TypeChecker.lean): the
  C++ kernel bounds the numerals its GMP fast paths accept and produce; lean4lean does not, and
  the one bound it does have has different behaviour. `~/lean4/src/kernel/type_checker.cpp`
  defines `check_nat_size` (`:298`), which throws a `kernel_exception` when a numeral exceeds
  `g_nat_max_size` (`LEAN_NAT_MAX_SIZE`, default **128 MB**), and applies it in `infer_lit`
  (`:319`), in `reduce_bin_nat_op` for `Nat.add`/`Nat.sub`/`Nat.mul` (`:656`), in `reduce_pow`
  (`:670`) and in `reduce_shiftLeft` (`:687`); `get_count_arg` (`:308`) throws separately when
  `Nat.pow`'s exponent or `Nat.shiftLeft`'s shift amount does not fit in `unsigned int`.
  lean4lean's `reduceBinNatOp` computes unconditionally, and `reducePow` bounds only the
  *exponent*, at `reducePowMaxExp = 1 <<< 24`, and on exceeding it **declines to reduce**
  (`return none`) instead of erroring — so `whnf` falls through to unfolding `Nat.pow`'s
  definition and evaluating it structurally. Inputs treated differently:
  * `Nat.pow 2 (2^25)`: C++ computes a 4 MB literal in milliseconds (its check is
    `size(base) > g_nat_max_size / exp`, i.e. `1 > 4`, which is false); lean4lean refuses the
    fast path and grinds through 2^25 unary steps on multi-megabyte numerals. **A complexity
    blowup on an input the C++ kernel handles instantly.**
  * `Nat.pow 2 (2^31)`, `Nat.pow 2 (2^33)`: C++ throws "the kernel refused to evaluate
    `Nat.pow`"; lean4lean behaves as above.
  * `Nat.shiftLeft 1 (2^40)`: C++ throws; lean4lean asks GMP for a 128 GB integer.
  * `Nat.mul` of two 100 MB literals, or a source literal larger than 128 MB: C++ throws;
    lean4lean computes it / accepts it.
  Neither direction is unsound — the C++ limit is a resource guard, not a typing rule, and
  refusing to reduce only makes `isDefEq` fail where it would have succeeded — but the accepted
  set and the running time both differ. Mirroring `check_nat_size` would remove the
  `reducePowMaxExp` hang as a side effect. Found by comparing `reduceNat` against
  `type_checker.cpp` while auditing the primitive recognizer; see `docs/handoff-primitive.md` §6.

* [`Lean4Lean.ElimNestedInductive`](Lean4Lean/Inductive/Add.lean) — **nested-inductive
  replacement is uncached.** Both substitution walks in the nested-inductive eliminator used
  `Lean.Expr.replace` / `Lean.Expr.replaceM`, each of which is `@[implemented_by]` an `unsafe`
  traversal keyed on a *pointer* map (`Lean.mkPtrMap`); C++'s `replace_fn`
  (`~/lean4/src/kernel/replace_fn.cpp`) does the same thing with an address-keyed cache. They
  now call `Expr.replaceNoCache` and `Expr.replaceNoCacheT` — the pure, structurally recursive
  versions the `implemented_by` pair is supposed to implement. Consequences:
  * **Logically none.** `Expr.replace`'s only stated relation to `replaceNoCache` in this repo
    was the frozen axiom `Expr.replace_eq` (`Verify/Axioms.lean`), which asserts exactly that the
    cached version *equals* the uncached one. **The clause that used to follow — "no proof in
    the tree ever used it" — was false**, and its evidence was a by-name grep. The axiom is
    `@[simp]`, so its one consumer was implicit: see the entry below. The state
    written by `replaceIfNested` is unaffected, because its own `nestedAux` memo is keyed on
    **structural** equality (`Iparams == e`) and is consulted before any auxiliary type is
    created — so re-visiting a structurally equal nested application still returns the same
    `_nested…` name and pushes no duplicate `newTypes`. Pointer caching was never what kept
    that idempotent.
  * **Complexity: a real blowup.** The pointer cache made each *shared* subterm of the
    constructor types under replacement cost one visit; without it, each *occurrence* costs a
    visit, so a DAG-shaped constructor type of depth `d` with two-way sharing at every level
    costs `2^d` instead of `d`. The inputs at risk are nested inductive declarations whose
    constructor types share large subterms — the C++ kernel handles those in time linear in the
    DAG. Measured after the change: the whole Kernel Arena suite is still correct (185 correct,
    6 `either`, 0 incorrect), with the two whole-library tests at `init` 1.4 min and `std`
    2.4 min and every nested-inductive test in the tens of milliseconds; no per-test baseline
    from before the change was retained, so this records absence of *failure*, not a timing
    comparison. Constructor types in practice are small and sharing in them is shallow, but the
    worst case is genuinely worse than C++'s.
  * **Why it was done anyway.** It removes `Lean.Expr.replaceM` — and, on the compiled path,
    core's `unsafe` `Expr.ReplaceImpl` — from the cone reachable from `Lean4Lean.addDecl`:
    `Verify/Guard.lean`'s check 3 drops from 52 to 51 flagged declarations, and of the *three*
    entries there that were genuine `@[implemented_by]`/`unsafe` implementations rather than
    equation-compiler artefacts, this was the only removable one (the other two are
    `ptrEqExpr`/`ptrEqConstantInfo`, deliberate and axiomatised). **It did not, on its own,
    make `Expr.replace_eq` unused** — that claim was retracted; removing the axiom's last
    consumer took the separate change recorded in the next entry.

* [`Lean4Lean.checkNoLooseBVars`](Lean4Lean/Inductive/Add.lean) (added 2026-09-01):
  `Environment.addInductive`'s pre-`run` guard loop **rejects** a member or constructor type
  carrying a **loose** bound variable. **The C++ kernel accepts such a declaration and silently
  reinterprets it**, so this is a divergence in the restrictive direction.

  The mechanism, verified against the C++ source: `elim_nested_inductive_fn::operator()` round-trips
  every constructor type through `get_params` and `lctx.mk_pi`, and `abstract` (`abstract.cpp`)
  rewrites only `fvar`/`mvar` nodes — returning `e` unchanged when `!has_fvar(e)`. So a loose bvar
  whose index is small enough to fall inside the parameter telescope is **captured** by a parameter
  binder, and the constructor type stored is not the one submitted. A declaration written
  `∀ (α : Type) (x : #1), Foo #1` at `np = 1` is stored as the ordinary `∀ α, α → Foo α`. When the
  index is too large to be captured, both kernels reject via the type checker — so the received
  wisdom "both kernels reject loose bvars anyway" is true only in *that* sub-case.

  **Why we diverge rather than match.** `Lean4Lean/Verify/Inductive/RunIdentity.lean` proves that
  without this check the specification — that the resulting environment realises a translation of
  the *submitted* declaration — is **false** (`not_addInductiveStepWF`). The only alternative repair
  is a closedness **premise**, and `Lean4Lean/Verify/ClosednessPropagation.lean` measures that as
  propagating all the way into `kernel_sound`'s statement, i.e. narrowing the main theorem. The
  guard changes no statement anywhere, because `Except.WF` holds vacuously of a rejection
  (`addInductiveStepWF_of_closed`). No unsoundness follows from the C++ behaviour — the stored
  declaration is well formed — so what is repaired is the specification, not a hole.

  **Nothing legitimate is refused, and that is proved rather than sampled**: `noLooseBVars_iff`
  shows the check decides exactly `looseBVarRange' ≤ d`, both directions. (Without the converse, a
  guard that rejected everything would satisfy the rejection obligation and pass every instrument
  in this repo.) A top-level `Expr` with a loose bvar is not a term of the type theory and no
  elaborator emits one; and a scan of the running environment found 0 of 10902
  inductive and constructor types affected. (An earlier version of this paragraph claimed "the
  Kernel Arena is unchanged at 185/6/0". That claim was **unfounded**: `lka.py run` does not
  build, and the harness had been measuring an Aug 21 source copy, so no arena run had exercised
  this check at all. See `docs/vacuity-ledger.md` rows 120-120c.)

  **Complexity.** `noLooseBVars` is an uncached structural recursion, where C++ reads the O(1)
  cached `looseBVarRange` header field, so on a heavily shared `Expr` DAG it is exponential in the
  sharing. This is not a new complexity class in this loop — the adjacent `checkNoNestedAux` already
  goes through `Expr.replaceNoCacheT` — but it is a real difference. Reading the cached field instead
  was rejected deliberately: its model agreement would drag `Lean.Expr.mkData_eq`'s side condition
  into every downstream consequence, whereas the pure check reaches **no frozen axiom at all**.

- **Uniform occurrence of the block's own types is checked inside the guard loop, not as a
  separate later pass** (`checkUniformIndOccs`, `Lean4Lean/Inductive/Add.lean`).

  C++ runs `check_uniform_ind_occs` as a pass *after* the whole
  `check_no_metavar_no_fvar`/`check_no_nested_aux` loop has finished
  (`kernel/inductive.cpp`, `add_inductive_fn::check_inductive_types`); lean4lean interleaves it
  into that loop, so a block violating both conditions gets a **different error message** from
  the two kernels. Both reject, so no accept/reject behaviour differs and the Kernel Arena is
  unaffected. `checkNoLooseBVars` already set this interleaving precedent.

  **Accept/reject is convergence, not divergence.** Before this check lean4lean *accepted* a block
  whose constructor mentions its own type applied to a non-parameter where C++ rejects it; the
  arena's `nested-nonuniform-param` flips from accepted to rejected with it, which is the C++
  behaviour. Proved rather than sampled in both directions:
  `Lean4Lean/Verify/Inductive/UniformOccMeasure.lean` shows the installed check decides the same
  condition (`uio_impl_eq`, seven pointwise clause equalities) and that nothing uniform is refused
  (`uio_impl_ok_of_occ`, plus 0 violations over 7013 submitted and 7215 post-elimination
  constructors). That converse is load-bearing here, not decoration: the pruning-free reading of
  the condition is identically false at every `nparams >= 1` (`uio_naive_too_strong`), i.e. it
  would reject `List`, so "rejects everything" was a live failure mode rather than a hypothetical.

  **Complexity.** C++'s `for_each_offset_fn` memoises on `(pointer, offset)`; `noNonUniformOcc` is
  uncached, so it is exponential in `Expr` DAG sharing where C++ is linear. Same class of
  difference as `checkNoLooseBVars` above, and for the same reason: the cached/pointer-keyed route
  would drag frozen `Lean.Expr` header axioms into every downstream consequence, while the pure
  check reaches no frozen axiom at all.

  C++ additionally rejects a `nparams` that is not `is_small()`; lean4lean's `nparams : Nat` has no
  counterpart. Pre-existing and unrelated to this check.
