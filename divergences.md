# Divergences from the Lean Kernel

This is a list of places where lean4lean deliberately has different behavior from the kernel. Unless specified here, any divergence between lean4lean and [lean4](https://github.com/leanprover/lean4/tree/master/src/kernel) is a bug.

* [`Lean4Lean.TypeChecker.Inner.reduceNative`](Lean4Lean/TypeChecker.lean): Lean4lean does not support reduction of `reduceBool`. This would involve implementing verified compilation, which while possible would be an additional chunk of work comparable to this entire repo.
* [`Lean4Lean.Environment.checkPrimitiveDef`](Lean4Lean/Primitive.lean), `checkPrimitiveInductive`: Lean does not check that primitives are declared with the correct types and definitional behavior, except in the case of `Eq` which is used in the declaration of `Quot`. This is required for soundness, but Lean is able to get away with it because Lean ships its prelude and using an alternative prelude is not supported. Four aspects of the check are stricter than "declared at a type definitionally equal to the expected one". First, for `Char.ofNat` and `String.ofList`, whose meaning the abstract model pins to a literal type (`∀ _ : Nat, Char` and `∀ _ : List.{0} Char, String`), the declared type is compared with `Expr.eqv` — structural equality up to binder names and binder info — rather than with `isDefEq`. A type such as `(fun _ : Nat => Nat → Char) Nat.zero` is definitionally the right one but is read off structurally as a different constant, so it is rejected. (This is available only for these two; the declared types of the `Nat` primitives carry `@&` borrow annotations, so they have no fixed structural shape to compare against.) Second, the equations for the `Nat` operations are checked under free variables introduced by `withLocalDecl`, so both sides of each comparison are well-typed terms; comparing `∀ _ : Nat, e₁` with `∀ _ : Nat, e₂` to get under the binder would decide the same equations, but on terms that are not types and therefore denote nothing in the model. Third, each branch requires up front that every constant whose *meaning* its equations rely on is already declared — `Nat` and `Bool` wherever the equations mention numerals or booleans, `Nat.ble` for `Nat.div`/`Nat.mod`, `Nat.add`/`Nat.div`/`Nat.mod`/`Nat.beq` for `Nat.bitwise`, `Nat.bitwise` plus `Nat`/`Bool` for `Nat.land`/`Nat.lor`/`Nat.xor`, `String`/`Char`/`List.nil`/`List.cons` for `String.ofList`, and `Nat`/`Bool`/`Nat.beq` inside the well-founded unfolding used by `Nat.gcd`/`Nat.bitwise`. Every one of these was already forced by a subsequent type-checking step in the same branch, so no declaration that used to be accepted is now rejected; stating them as explicit `env.contains` guards makes each branch's semantic dependencies visible, and lets the corresponding `VEnv.HasPrimitives` field be applied directly rather than recovered by inversion on a successful `checkType`. Fourth, the recognizer runs before `checkConstantVal`, so nothing it looks at has been type-checked; it therefore type-checks its own inputs (`checkPrimValue`, `checkIsType`, `checkedIsDefEq`, `checkedTypeIs`) instead of handing untyped terms to `isDefEq`, and compares against the *inferred* type of `v.value` rather than the declared `v.type`. This covers two distinct sources of untyped input: `v.type` and `v.value` themselves, and the other primitives the equations mention -- `Nat.pred` in the `Nat.sub` branch, `Nat.add` in `Nat.mul`, `Nat.bitwise`'s boolean combinator in `Nat.land`/`lor`/`xor`, and so on -- whose types `VEnv.HasPrimitives` does not pin, so that a right-hand side such as `Nat.add (mul y x) y` need not be well-typed either. Comparing untyped terms was not merely uninformative: `isDefEq` records its verdict in the `EquivManager`, whose well-formedness invariant requires both sides to be translatable, so a declaration such as `Nat.pred : (fun _ : NoSuchType => Nat → Nat) NoSuchValue := fun n => n` left an untranslatable term in that table (`bugs-found.md`). The declaration is rejected either way — `checkConstantVal` catches it a moment later, as does the C++ kernel — so the set of declarations `addDecl` accepts is unchanged, and the Kernel Arena is unchanged at 185/6/0. What does change is *which* check rejects a malformed primitive first, and hence the error message: a `Nat.add` whose declared type is not `Nat → Nat → Nat` now fails on the value's type, or on the mvar/fvar guard, rather than on the declared type. Cost is within noise (65.2 ms after, against 63.4 ms before, for the recognizer plus the body check over all 18 primitives, best of 5 x 40 iterations), and is ~0.08% of the 83 s the Kernel Arena's `init` test spends on 53090 declarations; the body check `addDefinition` runs afterwards shares the recognizer's `inferTypeC` entries.* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), literal case: The original code was not checking that the literal type actually exists. Again, this is okay provided that the prelude is trusted.
* [`Lean4Lean.TypeChecker.Inner.tryStringLitExpansionCore`](Lean4Lean/TypeChecker.lean): there is a counterproductive `whnf` call in this function which is removed in Lean4lean.
* [`Lean4Lean.TypeChecker.Inner.isDefEqApp`](Lean4Lean/TypeChecker.lean): lean4lean compares the two argument counts before the two heads, where `type_checker::is_def_eq_app` compares the heads first. Both answer `false` when the counts differ, so the decision is the same.
* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), application case: lean4lean checks `isDefEq dType aType`, where `infer_app` checks `is_def_eq(a_type, d_type)`. Definitional equality is symmetric, so this cannot change the answer, but this avoids some needless left-right flipping.
* [`Lean.Level.normalize`](https://github.com/leanprover/lean4/blob/v4.33.0-rc2/src/Lean/Level.lean), `isEquiv`, `geq`, `instantiateLevelParams`: Lean4lean uses the level operations from Lean's standard library, which differ from the C++ kernel's; [leanprover/lean4#14356](https://github.com/leanprover/lean4/pull/14356) tracks aligning them. This has two separate consequences. The comparison operations decide slightly different sets of (in)equalities than the kernel's `is_equiv`/`is_geq` (but see the next point). And because `instantiateLevelParams` builds levels with `mkLevelMax'`/`mkLevelIMax'` rather than the kernel's `mk_max`/`mk_imax`, unfolding a universe-polymorphic constant can produce a term that means the same as the kernel's but is not syntactically equal to it, and so does not share its `Expr.hash`.
* [`Lean.Level.normalize'`](Lean4Lean/Level.lean), `isEquiv'`, `geq'`: Lean4lean implements a new algorithm for level normalization. These run the standard library's operation as a fast path and fall back to a complete decision procedure for level algebra, so lean4lean decides level equality and `≥` for *more* pairs than either the standard library or the kernel — it accepts declarations the kernel rejects for reasons of level incompleteness, never the other way around.
* [`Lean4Lean.checkConstantVal`](Lean4Lean/Environment.lean): The original implementation would call `check` which sets the level params and then unsets them afterward, and then `ensure_sort` would run in a context without any level params. In lean4lean the monad is parameterized over level params, so they remain the same across the two calls.
* [`Lean4Lean.toCtorWhenStruct`](Lean4Lean/Inductive/Reduce.lean), `inferProj`: both kernels now recognize `Prop` using normalized universe levels ([leanprover/lean4#14613](https://github.com/leanprover/lean4/pull/14613)). Lean4lean remains more conservative for uncertain levels, using `isNeverZero` where Lean uses `!isAlwaysZero`. Lean's choice would be unsound if its level algorithm did not reject the true equation `imax 1 u ≤ u`: `inductive T.{u} : Sort u where mk : Bool → T` would otherwise permit an analogue of the construction in #14613.
* [`Lean4Lean.EquivManager.isEquiv`](Lean4Lean/EquivManager.lean), [`Lean4Lean.TypeChecker.Inner.isDefEqCore'`](Lean4Lean/TypeChecker.lean), `reduceProj`: when comparing two projections, and when reducing one, lean4lean uses only the projection index, while the C++ kernel also compares the structure name ([leanprover/lean4#14631](https://github.com/leanprover/lean4/pull/14631), [#14632](https://github.com/leanprover/lean4/pull/14632)). The name has already been checked by the time either happens: [`inferProj`](Lean4Lean/TypeChecker.lean) rejects `.proj S i e` unless the type of `e` whnfs to an application of `S` itself. Comparison and reduction only ever see projections that have been through type inference, so re-comparing the name there is redundant.
* [`Lean4Lean.Environment.addInductive`](Lean4Lean/Inductive/Add.lean): [leanprover/lean4#14621](https://github.com/leanprover/lean4/pull/14621) rechecks the declarations produced by nested-inductive elimination — the restored constructor types, the restored recursor types and the recursor rules' right-hand sides. Lean4lean does not. Upstream describes these as redundant sanity checks that "may prevent soundness bugs if the nested-inductive code is still missing any required validations"; they establish no precondition that a later step consumes. Lean4lean aims to prove the elimination correct rather than to recheck its output, and a speculative check would only add proof obligations without contributing an invariant. The check of the nested applications `I Ds` from [#14577](https://github.com/leanprover/lean4/pull/14577) is kept, because those arguments are dropped from the auxiliary declarations and so are not covered by checking the block.
* [`Lean4Lean.checkNoNestedAux`](Lean4Lean/Inductive/Add.lean): [leanprover/lean4#14616](https://github.com/leanprover/lean4/pull/14616) rejects the reserved `_nested` prefix in both the inductive types and the constructor types of a declaration; lean4lean checks only the constructor types. The bug that check fixes is specific to constructors: nested occurrences are rewritten to the auxiliary types in constructor types only (`replaceAllNested`), and rewritten back the same way (`restoreNested`), so an inductive's own type is carried through both directions verbatim and cannot acquire a type it was not checked at. A `_nested` name written in an inductive type also cannot resolve in the first place: the auxiliary types are declared in the same block, so they are not in the environment while that block's types are checked (unlike constructor types, which are checked once the block's types, auxiliaries included, are present), and they never survive into the final environment. Lean's check additionally reserves the whole `_nested` namespace against unrelated user declarations, which lean4lean does not.
* [`Lean4Lean.ElimNestedInductive.Result.restoreNested`](Lean4Lean/Inductive/Add.lean), `restoreCtorName`: [leanprover/lean4#14632](https://github.com/leanprover/lean4/pull/14632) turned the `lean_assert`s in the nested-inductive restoration into kernel exceptions; lean4lean keeps `unreachable!` and `assert!`. The branches are unreachable: `restoreCtorName` runs only for the recursors of the auxiliary types the elimination generates, whose constructors are exactly the keys of `aux2nested`, and the nested occurrences stored there are applications of a constant by construction. Upstream's stated motivation is that the assertions vanish in a release build and the C++ consumers then read out of bounds; the corresponding accesses here are total, so there is nothing to read out of bounds. Note that if one of these invariants were broken anyway, `unreachable!` would continue with a default value rather than reject; the restored constructor and recursor types are re-checked in the final environment ([#14621](https://github.com/leanprover/lean4/pull/14621)), which lean4lean retains, but a restored rule constructor *name* is not covered by that pass.
* [`Lean4Lean.TypeChecker.Inner.inferType'`](Lean4Lean/TypeChecker.lean), `.bvar` case: `type_checker::infer_type_core` writes `lean_unreachable()` in the `BVar` case; lean4lean throws the same `Kernel.Exception` the function's own entry guard throws for loose bound variables. The branch is unreachable in both: `infer_type_core` and `inferType'` both open with `if (has_loose_bvars(e)) throw …`, and a bare `.bvar i` has `looseBVarRange = i+1 > 0`, so it never reaches the `match`. The difference is only in what happens if that reasoning is ever wrong. `lean_unreachable()` is undefined behaviour in a release build; `unreachable!` in Lean is a `panic!`, i.e. `fun _ _ s => .ok (default, s)`, which *continues* with `default` — for `inferType'` that means returning an arbitrary `Expr` as the inferred type of a term, which is unsound. Throwing rejects instead, which is sound unconditionally. This also removes the branch's dependence on the [`looseBVarRange_eq`](Lean4Lean/Verify/Axioms.lean) axiom: `Expr.hasLooseBVars` reads the cached `looseBVarRange` field of the expression's `Data` word rather than recomputing it, and that field was not conservative before the fix of [leanprover/lean4#8554](https://github.com/leanprover/lean4/issues/8554) (`bugs-found.md`), so "the guard above already rejected every `.bvar`" is a claim about upstream data-word arithmetic, not a claim about the `match`. `inferType'.WF` now discharges the case with `.throw` — a rejection satisfies every `Except.WF` obligation vacuously — instead of deriving a contradiction from the guard. The set of accepted declarations is unchanged (Kernel Arena 185/6/0); no reachable input takes this branch. The same argument applies to the remaining `unreachable!`s in `getSortLevel`, `whnfCore'`, `isDefEqCore'` and `quickIsDefEq`, which have not been converted.
* [`Lean.Expr.cheapBetaReduce`](Lean4Lean/Instantiate.lean): where the C++ kernel drops the consumed arguments outright when `!fn.has_loose_bvars()`, lean4lean applies the (then trivial) substitution, returning `mkAppRange (fn.instantiateRevRange 0 i args) i args.size args`. `Expr.hasLooseBVars` reads the cached **20-bit** `looseBVarRange` field of the `Data` word, so it is `< 2^20` unconditionally and is wrong for a term whose `bvar` indices overflow it ([leanprover/lean4#8554](https://github.com/leanprover/lean4/issues/8554), `docs/axiom-audit.md` §3.1). If that bit ever reported "no loose bvars" for a body that has them, the C++ form would silently drop a substitution that is needed, which is unsound; the form here is a beta reduction whichever way the bit falls, so `BetaReduce.cheapBetaReduce` needs no side condition. When the bit is honest — always, at run time, since `lean_expr_mk_data` calls `lean_internal_panic` ("too many bound variables") and *aborts* rather than building such a term — `instantiateRevRange` is the identity and the value computed is unchanged. The C `lean_expr_instantiate_rev_range` returns immediately when the cached range is `0`, so the fast path is preserved too.

* [`Lean4Lean.TypeChecker.Inner.isDefEqLambda`](Lean4Lean/TypeChecker.lean), `isDefEqForall`: the C++ kernel skips the local declaration when `tBody.has_loose_bvars() || sBody.has_loose_bvars()` is false, pushing a placeholder into `subst` instead of a free variable; lean4lean always introduces the free variable. Same reason as `cheapBetaReduce` above: the test reads the untrustworthy cached 20-bit field, and a bit that wrongly said "no loose bvars" would have the two bodies compared with `default` (an undeclared constant) substituted for the binder — an instance check where a check under a binder is required. Whenever the bit is honest the two branches decide the same thing, because neither body looks at the pushed value, so the set of accepted declarations is unchanged (Kernel Arena 185/6/0). The cost is an extra local declaration, and an extra `sDom.instantiateRev subst`, per binder pair: 6% wall-clock on the whole Kernel Arena suite (251.3 s to 267.5 s), with the two large tests `init` (83.5 s to 89.1 s) and `std` (139.4 s to 148.0 s) accounting for essentially all of it and no `perf/*` test moving more than 5%.

* [`Lean4Lean.FuelConfig`](Lean4Lean/FuelConfig.lean): since [leanprover/lean4#13956](https://github.com/leanprover/lean4/pull/13956), the native kernel bounds mutually recursive checking through the `maxRecDepth` option. Lean4lean exposes several independent fuel counters instead, because its Lean definitions also need explicit termination witnesses. Replay comparison therefore uses each implementation's default bound unless an explicit lean4lean fuel configuration is supplied.
* [`Lean4Lean.addDefinition`](Lean4Lean/Environment.lean) (`unsafe` branch), [`addMutual`](Lean4Lean/Environment.lean): an `unsafe`/`partial` definition may be recursive, so its body is checked in an environment that already contains the declaration. The C++ kernel adds `constant_info(d)` there -- the full definition, value included -- so the body can delta-unfold the very constant being defined. Lean4lean adds it as an axiom of the same type instead: the body may still *refer* to the block's constants, but cannot unfold them. So for example `unsafe def foo : Nat := (fun (_ : foo = 1) => 1) rfl` is accepted by the C++ kernel, but rejected by L4L: checking the argument requires `foo =?= 1`, which succeeds by unfolding `foo` to its own body and reducing. Read literally, that rule makes a typing fact about the constant available while establishing it, and implementing this in `IsDefEq` directly degenerates completely, allowing even things like `unsafe def bar : Nat := "hi"` by using the typing judgment to justify itself. The gap is confined to `unsafe`/`partial` code, which carries no logical content.
* [`Lean4Lean.addMutual`](Lean4Lean/Environment.lean): lean4lean requires the declarations of a mutual block to carry the same universe parameters and to have distinct names. Both checks are in kernel PRs that are not yet released ([leanprover/lean4#14608](https://github.com/leanprover/lean4/pull/14608), [#14632](https://github.com/leanprover/lean4/pull/14632)); the released kernel checks only that the safety annotations agree. Lean4lean needs them rather than merely matching them: the block is checked under a single `M.run`, whose level parameters are fixed for the whole run, and the model adds the block's constants one at a time with `VEnv.addConsts`, which fails on a repeated name.
* [`Lean4Lean.VEnv.ParRed`](Lean4Lean/Theory/Typing/ChurchRosser.lean), `CParRed` (`K⁺` rule): the abstract parallel-reduction relation fires an ι-rule on a major premise that is not syntactically a constructor application, whenever the major premise's type is a `Prop` and the eliminator is not small (`¬pat_small`, i.e. `D.isLE = true`). The kernel does not: `toCtorWhenK` runs only when `isKTarget` holds — a single type, an `isAlwaysZero` level, and a single constructor **with no fields** — so `Eq` qualifies but `Acc` does not, and `Acc.rec C f x h` is a weak-head normal form for the checker while `Acc.rec C f x (Acc.intro x g)` reduces. The abstract relation is therefore strictly larger than the checker's reduction on exactly these terms.

  This is deliberate and it is forced. `NormalEq.parRed`'s `appDF`/`extra` case must produce a *common reduct*: from `f a ≡ₚ f₂ b` and an ι-step on `f₂ b`, it has to exhibit `e₁'` with `f a ≫* e₁'` and `e₁' ≡ₚ e₂'`. When `a ≡ₚ b` holds by `NormalEq.proofIrrel` — `a` an arbitrary proof, `b` a constructor application — no axiom about inductive declarations can close it, because every such axiom delivers a *definitional* equality `a ≡ b` while `≫*` is syntactic reduction. Carneiro's `K⁺` (`unique.tex:103`) is stated with a typing side condition precisely so that it can fire on an arbitrary `h`, and his `thm:gg_compat` discharges the case by asserting "it is a small eliminator" — which is exactly `pat_small`, and which is false for `Acc` and `Eq`. So the rule, not a side condition, is what does the work; `Params.pat_major_canonical` supplies only the canonical form and its typing, to justify the new rule's regularity (`ParRed.defeq`) and its orthogonality (the `pat_uniq` family).

  Soundness is unaffected. `kernel_sound` needs "the checker accepts ⟹ the abstract environment is well formed", so enlarging the abstract theory is the direction that helps; the burden moves to the consistency of the enlarged theory, and the model discharges it — every proof is interpreted as the single point, and `K⁺` fires only when the major premise is a `Prop`, so proof irrelevance validates it with no further hypothesis.

  What it costs: [`reduceRecursor.WF`](Lean4Lean/Verify/TypeChecker/WHNF.lean) can no longer be read off the `ParRed` development as an equality between the checker's reduction and the abstract one. It has to be proved as a *containment* — the checker's `whnf` step is one of the abstract relation's steps — with the `K⁺` steps simply having no checker counterpart. If that proof refuses to be an equality, this is why. A second, smaller cost: `CParRed.exists` becomes non-constructive, since deciding whether to fire `K⁺` needs the major premise's `Prop`-ness and the existence of a canonical form; `Classical.choice` is already in `Verify/Guard.lean`'s whitelist and the whole development is in `Prop`.

* [`Lean4Lean.anySubterm`](Lean4Lean/Inductive/Add.lean) (`hasIndOcc`, `isNestedInductiveApp?`, `checkNoNestedAux`): these three "does any subterm match?" tests used `Lean.Expr.find?`, i.e. [`Lean.Expr.findImpl?`](https://github.com/leanprover/lean4/blob/v4.33.0-rc2/src/Lean/Util/FindExpr.lean), an `@[extern "lean_find_expr"] opaque` constant with **no Lean body at all** — not `partial`, not `@[implemented_by]`, so nothing to unfold and nothing to prove about. `hasIndOcc` is what `checkPositivity` rejects on, so strict positivity — one of the two places an inductive declaration can be unsound — rested on a C function with no Lean-side model, and `Verify/Guard.lean`'s check 3 does not see it (it filters to constants defined in `Lean4Lean.*` modules). Since all three consume the result only through `.isSome`, the question is purely existential and the C traversal's order, short-circuiting and pointer cache are invisible to the answer; `anySubterm` asks it with a structural walk built on the repo's own total `Lean.Expr.replaceNoCacheT`, which visits exactly the node set `for_each_fn<true>` does (`~/lean4/src/kernel/for_each_fn.cpp`), and `Lean.Expr.findImpl?` leaves the checker's cone entirely. No new axiom, and `Verify/Guard.lean`'s check-3 count is unchanged at 54/54 — the walk introduces no new recursive constant, which matters because *every* recursive definition, structural or not, gets an `f._unsafe_rec` companion for code generation and check 3 counts those.

  **The divergence is in complexity, not in the answer.** `lean_find_expr` caches visited nodes on pointer identity, so it is linear in the *DAG*; `anySubterm` has no cache and is linear in the *tree*, so a term with shared subterms is walked once per path to it. On real input this is invisible: over the 314073 type and value expressions of a full `Lean` environment the uncached walk costs 1.6x on a predicate that never fires and 1.1x on one that fires early, and the Kernel Arena is unchanged within noise (`init` 84.3 s -> 85.3 s, mean of 3; `std` 148.2 s -> 138.9 s, mean of 2; suite 185/6/0 either way). On *crafted* input it is exponential: an inductive whose constructor argument type is a maximally shared DAG of `n` nodes (`t 0 = 1`, `t (n+1) = Nat.add (t n) (t n)`, constructor `mk : Fin (t n) -> Foo`) is accepted through `Lean4Lean.addDecl` in 9 ms for every `n` up to 1000 with `find?`, and in 51 ms / 664 ms / 2511 ms for `n` = 16 / 20 / 22 with `anySubterm` — a ~40-node declaration would hang the checker. The export format shares subterms by index, so such an input is constructible. Restoring linearity needs a visited-set keyed by an `Expr` equality, and the only ones available are upstream `@[extern] opaque` constants: `Expr.equal` (via `ExprStructEq`, modelled by the frozen `equal_eq` axiom but not currently in the cone) or `Expr.eqv` (in the cone, modelled by `eqv_eq`). Either would make the *answer* depend on an extern, which is what this change exists to undo, so the cache is deliberately omitted.

* [`Lean4Lean.AddInductive.checkPositivity`](Lean4Lean/Inductive/Add.lean), `isValidIndApp?` branch: the rejection message reads "arg #n of 'c' **has** a non valid occurrence of the datatypes being declared" where the C++ kernel's reads "**contains** a non valid occurrence". Wording only — accept/reject agrees on every probe of `Lean4Lean/Tests/KernelHardening.lean`'s positivity-scope block, which runs each declaration through both kernels and fails the build if they disagree. The neighbouring "non positive occurrence" message is identical in both.

* [`Lean4Lean.AddInductive.consumeAnnotations`](Lean4Lean/Inductive/Add.lean): the thirteen `withLocalDecl` sites of the inductive adder record the annotation-stripped binder domain as the local-context type, mirroring `consume_type_annotations` at [`src/kernel/inductive.cpp:222,227`](https://github.com/leanprover/lean4/blob/v4.33.0-rc2/src/kernel/inductive.cpp). They no longer call `Lean.Expr.consumeTypeAnnotations` to do it. That function is `partial`, hence an `opaque` with **no Lean body at all** — the same situation as `Lean.Expr.findImpl?` before `anySubterm`, and equally invisible to [`Verify/Guard.lean`](Lean4Lean/Verify/Guard.lean)'s check 3, which filters to constants defined in `Lean4Lean.*` modules. It reached eleven distinct binder-introducing loops (`checkInductiveTypes`, `checkConstructors`, `checkPositivity`, `isRecArg`, `isLargeEliminator`, and all six of `mkRecInfos`), so every abstract local context the adder builds rested on a constant nothing could be proved about; [`M.WF.elim_loop`](Lean4Lean/Verify/Inductive/Add.lean)'s `hcta` hypothesis is what that cost, and it is false on ~2% of the constructors of a real environment. The replacement is `Nat.repeat stripAnnotation` over a non-recursive one-step matcher, which adds **no** new recursive constant — a fresh structural recursion would acquire an `_unsafe_rec` companion and enlarge check 3's frozen list, the same constraint that made `anySubterm` delegate to `Expr.replaceNoCacheT`. Check 3 is unchanged at 54/54, and the cone's body-less opaque count drops from 48 to 47.

  **The divergence is the fuel bound, and it is a rejection.** `stripAnnotation` is the identity at its fixpoint, so iterating past the fixpoint is harmless; what the bound rules out is annotation nesting deeper than `FuelConfig.inductiveFuel` (default 1000), which lean4lean rejects with `.deepRecursion` where the C++ kernel would strip it. Returning a half-stripped type instead would put a merely *definitionally* correct type into the local context and silently change what later `isDefEq` calls see, so rejecting is the sound choice and it preserves the property the rest of that file relies on, that more fuel only ever enlarges the accepted set. Behaviour is otherwise identical: checked against the opaque over every binder domain of every constructor and inductive type of a full `Lean` environment — **15988 compared, 15988 agree, 0 disagreements, 0 fuel rejections** — and that check is a build-time regression in [`Tests/KernelHardening.lean`](Lean4Lean/Tests/KernelHardening.lean). Unlike the other loops in the file this one always runs to its bound rather than exiting early, so its cost is linear in `inductiveFuel`; at the default it is ~10x the extern on a microbenchmark of the function alone (1626 ms vs 160 ms for 20 passes over all 15978 binder domains of a full `Lean` environment, identical checksums), which is ~73 ms per single pass, and the Kernel Arena is unchanged at 185/6/0 with `init` 82.2 s and `std` 139.6 s, both inside the band already recorded above.

* [`Lean4Lean.AddInductive.checkConstructors`](Lean4Lean/Inductive/Add.lean), [`ElimNestedInductive.Result`](Lean4Lean/Inductive/Add.lean), `restoreNested`, `mkAuxRecNameMap`: the duplicate-constructor guard and the nested-restoration maps no longer use `NameSet`/`NameMap`. Those are `RBTree`/`RBMap` ordered by [`Lean.Name.quickCmp`](https://github.com/leanprover/lean4/blob/v4.33.0-rc2/src/Lean/Data/Name.lean), which carries `@[implemented_by quickCmpImpl]`, and `quickCmpImpl` opens `if unsafe ptrEq n₁ n₂ then .eq` — so the **executed** path runs through `quickCmpImpl.unsafe_impl_2`, a body-less `opaque`. That is a verified/executed divergence of exactly the kind [`Verify/Guard.lean`](Lean4Lean/Verify/Guard.lean)'s check 3 exists to catch, sitting upstream where check 3 structurally cannot see it (it filters to constants defined in `Lean4Lean.*` modules). It matters more here than a hash lookup would: a `PersistentHashMap` hit is re-confirmed by an equality test, so a wrong hash causes a miss and not a wrong answer, whereas a **tree** lookup's answer is not re-confirmed by anything — a comparison that wrongly reported `eq` would silently accept a duplicate constructor, or restore the wrong nested type. The replacements are plain `List Name` / `List (Name × α)` with `List.contains` and `List.lookup`, i.e. `Lean.Name.beq`, whose Lean body *is* its specification (it is `@[extern "lean_name_eq"]`, so the C is required to implement that body, rather than there being no body at all). No new recursive constant is introduced — `List.contains`/`List.lookup`/`List.forM` are upstream, and a fresh structural recursion here would acquire an `_unsafe_rec` companion and enlarge check 3's frozen list. Check 3 is unchanged at 54/54, the Kernel Arena is unchanged at 185/6/0, and `Lean4Lean.Environment.addInductive` no longer names `Name.quickCmp` at all.

  **The divergence is in complexity, and the semantics of `insert` are preserved.** `NameMap.insert` is last-write-wins and `RBMap` lookup is `O(log n)`; a cons plus `List.lookup` is also last-write-wins (the first match found is the most recently pushed) but is `O(n)`, and the duplicate-constructor scan is `O(n²)` in the constructor count where it was `O(n log n)`. The counts involved are small — constructors of one inductive type, and auxiliary types generated by nested elimination, which `numNested` now reads as a list length rather than a tree size (`mkUniqueName`'s outputs are pairwise distinct, so the two agree). The Kernel Arena is unchanged within noise.

  **What remains.** `Name.quickCmp` cannot leave `Lean4Lean.addDecl`'s cone, and the reason is structural rather than fixable in this repo: `Lean.LocalContext`'s field `auxDeclToFullName : FVarIdMap Name` names it in its *type*, and `FVarIdMap` is an `RBMap` keyed by it, so every lean4lean function whose type mentions `LocalContext` reaches it. This kernel never writes that field — it is `{}` on every `LocalContext` it builds, and `RBMap.empty` never calls the comparator — so the reachability is type-level only. One *executed* use is left, [`Lean4Lean.addMutual`](Lean4Lean/Environment.lean)'s mutual-block duplicate-name guard; `Lean4Lean/Tests/KernelHardening.lean`'s `quickCmpExecutors` is the frozen list that tracks it, and the same file's "mutual block with a duplicate name" probe is what would catch a regression in it.
